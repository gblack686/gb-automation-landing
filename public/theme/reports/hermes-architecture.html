Hermes Architecture & Agentic Loops

How GBAutomation's single agent runtime works — profiles, canopy, managed cron, Kanban dispatch, observability — and the agentic loops built into it, mapped onto the 2026 loop-engineering taxonomy.

01Overview140 words

Hermes is GBAutomation's single agent runtime (OpenClaw retired 2026-06-20). It runs on the always-on Mac Mini and is, structurally, a fleet of agentic loops: profile-defined agents, cron-triggered with model-assessed receipts, dispatched through one Kanban board, every action traced and written to durable Supabase surfaces.

This document maps the seven subsystems and uses the smoke-client tenant — the synthetic tenant whose entire purpose is to verify the stack end-to-end — as the worked example throughout. Profile source of truth: second-brain/systems/hermes-profiles/smoke-client/profiles/smoke-client.yaml (schema hermes-profile-spec.v1).

The receipt-first invariant: every agent action is traced (Langfuse), every cron outcome is assessed by a mini model, and every unit of unattended work flows through a single Kanban board. Nothing claims to have happened without citing a durable row, trace, or receipt.

03Profilestable

Binding an agent to skills, model, prompts, and the data surfaces it may touch.

A profile is a YAML spec (hermes-profile-spec.v1) that binds a Hermes agent to its runtime, model, tools/skills, prompt sources, observability contract, and the Supabase data surfaces it's allowed to touch.

Key smoke-client fields: model: gpt-5.5, provider: openai-codex, primary_tools (canopy, hermes-ci-gate, hermes-cron-manager, hermes-kanban, langfuse, supabase), observability.telemetry_contract: hermes-card-observability.v1, a 20-table data_surfaces list, and hard_gates (canopy lint, prompt-inventory indexed, profile present, no-real-client-data).

!
CI invariant: three sources pin the same fields (primary_tools, observability.required_skills, data_surfaces). Edit the canonical spec first, reconcile by reference — CI fails on divergence. The smoke-client also runs a two-core second brain: gbauto-core/ (public, indexed) + client-core/ (real PII, excluded from every anon surface).

Durable outputs per tick: cron_runs (aggregate: ok/fail counts, elapsed_ms, total_cost_usd), cron_run_outputs (per-tick summary + status), host_job_runs (cross-host receipt), hermes_cron_catalog (last_green_at advanced only on ok), a Langfuse span, and a Kanban card.

Paused → active deploy gate (jobs ship state: paused): (1) validate_managed_manifest.py schema check, then (2) the validate-cron-deploy 11-check skill (task registered, wrapper wired, gbauto-supabase CLI present, smoke-fire, receipt on disk, Supabase row, round-trip ≤60s).

⚠
On the Mac Mini, crons shelling gbauto-supabase must export PATH=$HOME/.local/bin or they silently 100%-fail. Windows jobs use Invoke-WithReceipt.ps1 instead.

Every card body embeds a TAC prompt packet (tac-cli.team-dispatch.v1 + tac_prompt_format.v1): purpose, variables, instructions, workflow, report, plus hard_gates (reuse evidence, validation, smoke, PR/commit) and the hermes-card-observability.v1 surface spec. tac-validator is the loop's evaluator — it can bounce work back to tac-builder. Closeout protocol (2026-06-16): every terminal parent closes as merged (preferred), committed_unmerged, receipt_only, blocked_with_receipt, or superseded.

10Loop engineering — the concept180 words

The 2026 paradigm (Steinberger / Osmani): design the loop, not the prompt.

Each layer wraps the previous rather than replacing it:

LayerEraWhat you optimize
Prompt engineering2022–2024Word choice of a single turn
Context engineering2025Everything the model sees at inference
Harness engineering2026The full scaffold around the agent
Loop engineering2026The iterative cycle that keeps the agent moving toward a goal unattended

Loop engineering (Peter Steinberger, June 7 2026; vocabulary by Addy Osmani): "the practice of designing the system that prompts, checks, remembers, and re-runs an AI agent — instead of you typing every next instruction by hand." The leverage moved from the prompt to system architecture: the quality of the trigger, the precision of the goal, and the design of the verification step.

The canonical loop anatomy

Every agentic loop reduces to observe → think → act → evaluate → loop, and needs: a trigger; a verifiable goal (testable termination, not a vibe); environment tools; environment feedback (real results, not just reasoning); a separate evaluator that decides if the goal is met; context management; and stop / escalation logic.

Required safeguards

Or the loop "runs until the money runs out": a hard iteration cap, a token/cost budget, no-progress detection, circuit breakers, verifiable termination (not the agent's self-assessment), and human checkpoints before irreversible actions.

A · Control & build

① Cron receipt loop — evaluator-optimizer · LIVE  The keystone. Trigger: schedule. Evaluator: a separate gpt-5-mini ASSESS step grades the run — textbook "separate evaluator decides if the goal is met". Stop: last_green_at advances only on ok. Safeguards: budget cap + atomic lock, fail-fast schema gate, paused-by-default until the 11-check deploy gate passes.

② TAC build loop — multi-agent orchestration + Reflexion · LIVE  The 8-role Kanban team. Evaluator: tac-validator bounces work back to tac-builder (the Reflexion inner loop). Stop: terminal parent closes in an explicit state. Safeguards are the fragile part (historic retry-cap gap), not the structure.

B · Ingestion — observe → extract → store → readback

⑦ YouTube intel ingestion loop · partial  Scheduled scan → extract intel → --sync-supabase → obs_youtube_* (#322). Evaluator: sync receipt + row presence. 0 rows until run on the Mini (PC DNS-blocked); view still TODO.

⑧ Meet transcript → triage loop · partial  Email/Drive trigger → transcript_agent.py → Claude extracts issues + action items → durable session todos → human-gated triage cron (#295) → Kanban. Evaluator: human gate. transcript_agent on-demand (no launchd); triage cron live.

⑨ Inbox / email-watcher triage loop · LIVE  email_watcher.py every 30 min → classify → draft replies + Telegram. Evaluator: classifier + draft-first human approval (never auto-sends).

C · Knowledge & analytics

⑩ Knowledge-compilation loop (LLM-wiki + QMD tag-lineage) · partial  Sources change → compile_wiki/compile_knowledge + graphify + tag extractor --sync-supabase → tag_observations + views + wiki articles (#307-312). Evaluator: tag-lineage golden thread + smoke-validate. Views LIVE; observations 0 until extractor syncs on the Mini.

⑪ PRD→commit rollup analytics loop · advisory  Commits + PRDs land → index_prds.py --sync-supabase (227-row spine) + morning_brief.py commits-by-client + build_plan_execution_dossiers.py (joins Kanban + Langfuse + codex + git). Evaluator: advisory-only — no hard gate. github_commits spine UNAPPLIED (DNS split).

⑫ Error-telemetry backfill loop · LIVE  langfuse / CloudWatch / Hermes → app_error_events, re-runnable (#333/#339). Evaluator: idempotent re-run + row counts. GCS offload leg blocked on reauth.

D · Verification & gate

④ Smoke-client verification loop — the loop that tests the loops · LIVE  The whole smoke-client tenant is one verification loop over the stack. Evaluator: smoke-validate + the hard rule — cite a durable surface or say "unavailable". Stop: all hard gates green.

③ Feedback-triage loop — human-checkpoint · LIVE  Feedback → indexed context → proposal card → mandatory human gate (human_gate_required: true). Telegram callbacks propose but never dispatch. Loops ⑧ and ⑨ feed into it.

E · Learning & interaction

⑤ Self-improve loop — Reflexion at the fleet level · partial  tac-self-improve + the 14-feedback-loops LEARN tier. Trigger: a build closes. Evaluator: next build's reuse-evidence gate (delayed, soft).

⑥ MCP / chat poll loop — ReAct over a transport · gated  Portal chat HermesTransport seam + MCP events_poll/events_wait. Wired but gated behind PORTAL_HERMES_TRANSPORT.

+
Emerging (loop-shaped, not yet first-class): task-telegram-notify (3 crons → DM fan-out), the Commit Cleaner hourly WIP-snapshot safety loop, and the ECOM hourly monitoring lane — each has a trigger + action but a thin/absent evaluator today.
