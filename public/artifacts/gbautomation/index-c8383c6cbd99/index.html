02 1. Summary 48 words

Give the operator a traceable view of which TAC components were retrieved and which builds they led to. This is provenance/observability, not metrics — no scoring, no coverage percentages. The goal is to open a build and see its components, or open a component and see its builds.

03 2. Problem (the edge does not exist yet) 102 words

Three receipt stores, zero linkage between them:

  • second-brain/intelligence/tac-retrievals/*.json (tac-component-retrieval.v1) lists matched_components[] (repo / path / primitive / score) but carries no run_id, no PRD reference. A retrieval does not know which build consumed it.
  • second-brain/intelligence/tac-validations/tac-*.json (tac-build-run.v1) carries run_id + source.identifier (the PRD) + skills[], but never names the retrieved components or the retrieval artifact that fed it.
  • Supabase tac_component_retrievals is keyed on retrieval_id (filename stem); there is no build foreign-key column.

So "which components → which builds" cannot be answered today because nobody writes that edge. The work is to mint the edge at write-time, then browse it.

04 3. Goal 49 words
  1. Stamp a durable, exact edge between each retrieval and the build that consumed it, at write-time.
  2. Make the edge queryable in Supabase and browsable as a local HTML lineage view.
  3. Fold the reverse lookup ("also pulled by builds X, Y") into the existing Build Review report.
05 4. Locked decisions 45 words
  • Forward-only. Stamp the edge starting with the next build. Existing receipts stay unlinked — no fuzzy timestamp/query reconstruction. (Decided 2026-05-27.)
  • Both surfaces. Local HTML artifact for offline browsing now + a Supabase column so the edge is queryable and feeds a future weekly cron. (Decided 2026-05-27.)
06 5. Non-goals 55 words
  • No utilization metrics, coverage scores, or effectiveness ranking — build_tac_retrieval_effectiveness.py already owns scoring and is explicitly out of scope here.
  • No backfill of historical receipts.
  • No new retrieval engine — reuse resources/lib/tac_retrieval.py and the existing receipt stores.
  • No change to how components are selected; this only records and surfaces what was already chosen.
07 6. Architecture / Phases 256 words

Phase 1 — Mint the edge at write-time

  • scripts/retrieve_tac_components.py: add --build-run-id and --prd arguments; write build_run_id and prd_identifier into the emitted artifact (default null when run standalone).
  • Build path (scripts/tac_build_dry_run.py and any orchestrator that triggers retrieval during a build): record a reciprocal retrieval_ref (artifact path) plus a compact components[] summary (repo, path, primitive, score) into the tac-build-run.v1 receipt.
  • Contracts: add build_run_id + prd_identifier to resources/skills/tac-data-output-patterns/references/tac-build-run.schema.json; create a sibling tac-component-retrieval.schema.json so the edge is contract-locked rather than implicit in code.

Phase 2 — Supabase column (queryable half of "both")

  • Additive, nullable migration via the gbauto-supabase CLI: add build_run_id + prd_identifier to tac_component_retrievals.
  • scripts/upsert_tac_component_retrieval_to_supabase.py: send the two new fields so tac_component_retrievals joins tac_build_runs on build_run_id.

Phase 3 — Local lineage HTML (browse-now half of "both")

  • New scripts/tac_lineage.py (reuses resources/lib/tac_retrieval.py + receipt walkers): join tac-retrievals/ with tac-builds/ and tac-validations/ on build_run_id; emit a bipartite view at artifacts/tac-lineage/index.html — open a build to see its components (each linked to its inventory entry), open a component to see its builds.
  • Surface the two orphan lists that reveal pipeline leaks: retrieved-never-built and built-with-no-retrieval.
  • Style follows the Build Review surface (blue eyebrow + pills, cream canvas) so it slots into the same review reflex.

Phase 4 — Fold into Build Review + cadence

  • scripts/render_tac_report_package.py "TAC components" section: link each component row to its inventory source and show "also pulled by builds X, Y."
  • Weekly cron: read the Supabase join, refresh artifacts/tac-lineage/, and send a Telegram one-line summary.
08 7. Data contract (the edge) 34 words

tac-component-retrieval.v1 gains:

{
  "build_run_id": "tac-20260527T... | null",
  "prd_identifier": "2026-05-27-... | null"
}

tac-build-run.v1 gains:

{
  "retrieval_ref": "second-brain/intelligence/tac-retrievals/<file>.json | null",
  "components": [
    {"repo": "string", "path": "string", "primitive": "schema", "score": 12}
  ]
}

Join key everywhere: build_run_id.

10 9. Acceptance criteria 75 words
  • A build run produces a retrieval artifact stamped with its build_run_id + prd_identifier.
  • The build receipt names retrieval_ref and embeds a compact components[] summary.
  • tac-component-retrieval.schema.json exists and validates a stamped artifact.
  • New Supabase tac_component_retrievals rows carry build_run_id; the join to tac_build_runs returns matched edges.
  • python scripts/tac_lineage.py opens artifacts/tac-lineage/index.html showing build-to-component and component-to-build, plus the two orphan lists.
  • Build Review "TAC components" rows link to inventory and show reverse builds.
