02 1. Summary 141 words

Ship the "agent + watch loop" half of The Mall App backend and surface it on the GBAutomation site. Three deliverable surfaces:

  • Surface A — Scanner v2 (backend): upgrade the running mall-scraper Hermes profile + social-catalog-scraper skill to write rows per scrape, walk IG past the 12-post cap, download images, run on a schedule, diff against the previous run, and alert on sale / net-price change.
  • Surface B — Supabase data layer: four canonical tables (mall_brands, mall_items, mall_price_history, scrape_runs) so brand catalogs, price history, and per-run telemetry are queryable.
  • Surface C — Site mini-app: a read view at /apps/mall-scanner in gb-automation-landing, registered in the apps gallery so the build appears next to Logo Motion, YouTube Intel, and the other mini apps.

"Done" is not just the scraper running — it is the mini-app card live in the gallery with a working launch into a live read view.

03 2. Surfaces 286 words

Surface A — Scanner v2 (backend)

Upgrades on the v1 already running (see Sprint 1 PRD § 4 for the full v1-vs-v2 table):

  • WooCommerce adapter (IG + Shopify already implemented).
  • IG pagination past the 12-post cap via the timeline_media cursor pattern.
  • Per-scrape writes to Supabase (Surface B tables).
  • Image handling (Supabase Storage bucket or link-only — pending Sreya, default link-only).
  • Scheduled run via launchd, wrapped in the canonical Invoke-WithReceipt equivalent (env materialization via scripts/launchd_secrets_wrapper.sh — no inline credentials in the plist).
  • Diff logic against mall_price_history; alert on item.on_sale / item.price_drop through the @gbauto_hermes_bot Telegram path.

Surface B — Supabase data layer

Four tables, DDL in Sprint 1 PRD § 5 (001_mall_brands.sql → 004_scrape_runs.sql). All migrations and inserts route through the gbauto-supabase CLI. raw_json retained on every row so columns can be re-derived after Sreya's § 7 schema answers.

Surface C — Site mini-app (the gallery requirement)

Lands the build in gb-automation-landing mirroring the YouTube Intel pattern:

  1. Registry entry in public/portfolio/apps-registry.json:

  1. Route in src/App.jsx: <Route path="/apps/mall-scanner" element={<RequireAuth><MallScanner /></RequireAuth>} /> (mirrors the /apps/youtube-intel route).
  2. Page MallScanner.jsx + client lib (src/lib/mallScannerClient.js) reading the live mall_ tables through an /api/mall-scanner/ endpoint (same shape as youtubeIntelClient.js → /api/youtube-intel/dashboard): brands tracked, current catalog per brand, recent item.on_sale / item.price_drop events.
  3. latest_run card field wired from the newest scrape_runs row.
  4. Thumbnail poster under public/portfolio/samples/mall-scanner/.

05 4. Acceptance criteria 128 words

Backend + data (from Sprint 1 § 11):

  • Agent runs unattended ≥48 h on the Mac Mini with no crashes / manual resets.
  • ≥3 brands tracked end-to-end — catalogs in mall_items, history in mall_price_history, queryable in Supabase.
  • ≥1 real item.on_sale / item.price_drop event fires through the chosen alert channel.

Site mini-app (the gallery requirement):

  • apps-registry.json has the mall-scanner entry; the card renders in the apps gallery next to the other mini apps.
  • /apps/mall-scanner loads behind RequireAuth and shows the live read view (brands, catalog, recent sale/price-drop events) from the mall_* tables.
  • The card's latest_run reflects the newest scrape_runs row.
  • Thumbnail poster renders on the card.

Build hygiene:

  • Build Review HTML rendered from the run receipt; status honest (executed vs dry-run).
  • Verifier report passes; Supabase rows verified by readback.
