Recommended architecture

  • Keep one stable Telegram bot username per operator surface.
  • Represent active board through name, short description, description, and command scopes.
  • Send board badge/status messages after context switches.
  • Use separate bots only for truly separate audiences or permissions.
  • Throttle identity writes: on board switch or daily, not per card.
  • Keep avatar stable; if changed, use setMyProfilePhoto only with explicit ops receipt.

Operational risks

  • Username churn breaks t.me links, mentions, saved contacts, and expectations.
  • Client caching can make visual identity changes lag or appear inconsistent.
  • Over-rotating bot name/photo weakens user trust and auditability.
  • Command scopes are hints; backend must still authorize every command.
  • setChatPhoto can affect shared groups/channels and needs admin rights.
