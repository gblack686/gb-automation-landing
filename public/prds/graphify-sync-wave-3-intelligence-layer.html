graphify-sync Wave-3 — Intelligence Layer

Wave 1 (local execution) and Wave 2 (Supabase lakehouse + 5 YAML taxonomies) ship the plumbing. Wave 3 makes the graphs themselves smarter so downstream agents (Finn, OpenClaw, weekly-alignment-check) can actually reason over them instead of grep-ing graph.json.

1. Why now

Wave-2 gave us:

  • 1 graph_runs row per scan with countable status
  • N graph_entities rows per run (typed via entity_types taxonomy)
  • M graph_edges rows per run (typed via edge_types taxonomy)
  • A 5-file YAML registry under second-brain/knowledge/taxonomies/

But every entity is just {id, type, name} and every edge is {source, target, type}. We can count things now. We still can't rank them, can't find them by similarity, and don't know which graphs are stale. Wave-3 fixes those three.

The repo has shipped +226K net lines / 249 commits / 759 files since 2026-05-15, so even the freshest graphs are already drifting. Wave-3 is the layer that lets us notice that.

2. Goals (countable)

  1. Every entity carries structured properties (line-count, last-modified, author, file-size, language)
  2. Every edge carries a numeric weight (mention-count, co-occurrence-count, last-touched)
  3. Every entity has an embedding in pgvector (768-dim, MiniLM-L6 or bge-small)
  4. A single Python entry point graphify_query.py answers 5 question shapes (see §5)
  5. A graph_freshness view ranks repos by staleness score (commits-since-last-graphify × file-touch-density)

3. Non-goals

  • LLM-rewriting of graphs (we use embeddings only for retrieval)
  • A web UI (CLI + Python lib only; UI is a later wave if needed)
  • Cross-client entity merging (each client repo stays isolated for RLS)
  • Replacing graphify itself — we enrich its output, never fork it

4. Agent team (4 specialists)

Follows TAC convention: each specialist owns one Phase and has a tight Done definition.

4.1 entity-property-extractor (Phase A)

  • Owns: resources/lib/graph_entity_enricher.py
  • Reads: graphify-out/graph.json for a repo
  • For each entity (file, symbol, concept):

- If entity_type='file': run wc -l, git log -1 --format=%aN,%aI, stat, language via extension map

- If entity_type='symbol': count lines in the symbol's span, owning file's last-author

- If entity_type='concept': count how many files mention it (from existing edges)

  • Writes: enriched entity row with properties JSONB column
  • Done when: properties non-null for >= 95% of entities across 9 client repos
  • Skill citation: extends graph_lake_writer.py from Wave-2 (resources/lib/graph_lake_writer.py:74-118)

4.2 edge-weight-scorer (Phase B)

  • Owns: resources/lib/graph_edge_weigher.py
  • For each edge (source, target, type):

- mentions: count occurrences of target.name in source.body

- co_touch: count git commits that touched both source.path and target.path in last 90 days

- recency: exp(-days_since_last_touch / 30) exponential decay

  • Composite weight: 0.5mentions_z + 0.3co_touch_z + 0.2*recency (z-scores per repo)
  • Writes: graph_edges.weight FLOAT and graph_edges.weight_components JSONB
  • Done when: every edge has weight non-null; weights normalized 0-1 per repo
  • Pitfall: don't re-score every edge every run — only edges whose source/target changed since last_run

4.3 entity-embedder (Phase C)

  • Owns: resources/lib/graph_embedder.py
  • Embedding model: BAAI/bge-small-en-v1.5 (384-dim, runs CPU-local, no API cost)
  • For each entity, embed f"{entity_type} {name}\n\n{summary or first 500 chars of body}"
  • Storage: pgvector column embedding vector(384) on graph_entities
  • HNSW index for cosine similarity, m=16, ef_construction=64
  • Done when: embedding non-null for >= 95% of entities; similarity query under 50ms p95 on 50K entities
  • Pitfall: bge-small needs sentence-transformers on the Mac Mini — pin version, document in requirements.txt
  • Migration: db/migrations/2026-05-19_pgvector_embeddings.sql

4.4 query-api-author (Phase D)

  • Owns: resources/skills/graphify-sync/scripts/graphify_query.py
  • 5 question shapes (CLI flags + matching Python functions):

- --similar <entity_name> → top-k by cosine similarity in same client

- --neighbors <entity_name> → 1-hop outgoing edges sorted by weight desc

- --hottest <client> → entities with most edges touched in last 7 days

- --orphans <client> → entities with degree=0 (graphify thinks they exist but nothing references them)

- --freshness → all clients ranked by staleness score

  • Output: pretty Telegram-safe text by default, --json for machine
  • Done when: all 5 flags pass smoke tests with real graphify-out data
  • Skill citation: reuse outbound_supabase_writer.py urllib pattern (~/.hermes/lib/outbound_supabase_writer.py)

5. New Supabase schema (single migration)

db/migrations/2026-05-19_graph_intelligence.sql:

-- Wave-3 columns on Wave-2 tables (additive only, no breaks)

alter table graph_entities
  add column if not exists properties jsonb default '{}'::jsonb,
  add column if not exists embedding vector(384);

alter table graph_edges
  add column if not exists weight float default 0.0,
  add column if not exists weight_components jsonb default '{}'::jsonb;

-- HNSW index for vector similarity (cosine distance)
create index if not exists graph_entities_embedding_idx
  on graph_entities using hnsw (embedding vector_cosine_ops)
  with (m = 16, ef_construction = 64);

-- B-tree index for weight-sorted neighbor queries
create index if not exists graph_edges_weight_idx
  on graph_edges (run_id, source_entity_id, weight desc);

-- View: graph freshness per client repo
create or replace view graph_freshness as
select
  r.client_slug,
  r.repo_path,
  max(r.completed_at) as last_graphify_at,
  extract(epoch from (now() - max(r.completed_at))) / 3600 as hours_since,
  (select count(*) from graph_entities where run_id = max(r.id)) as entity_count,
  (select count(*) from graph_edges where run_id = max(r.id)) as edge_count
from graph_runs r
where r.status = 'success'
group by r.client_slug, r.repo_path
order by hours_since desc;

Pre-req: create extension if not exists vector; (already in the Supabase project per Wave-2; verify in §11 step 0).

7. Pitfalls (learned from Wave 1+2)

  1. Don't call record_skill_run() inside Wave-3 scripts — the GBA-447 Stop hook already does it. Duplicate row trap.
  2. bge-small needs the venv to have torch + sentence-transformers. Mac Mini venv at ~/.openclaw/workspace/venv/ is the right one. Document in requirements.txt.
  3. pgvector dim mismatches are silent. vector(384) is the only shape that should ever go in. If we change models, write a migration that drops + recreates the index, never alter type.
  4. Edge weights drift. Re-score on every run for changed edges only, full re-score weekly (Sunday 03:00 PT cron tick).
  5. Embeddings cost CPU. Skip re-embedding when entity body hash unchanged (properties->>'body_sha256' check).
  6. graph_freshness view must use r.completed_at, not r.started_at — otherwise we count failed runs as fresh data.
