Section 1 Product Overview

What we ship

A two-phase upgrade to ~/repos/gbautomation/resources/skills/graphify-sync/:

Phase A (small): Rip out the SSH-to-self plumbing. Graphify-sync now runs entirely as local subprocess calls because Hermes lives on the same Mac Mini that hosts the client repos. Fix the broken per-client paths in config/repos.json to match actual on-disk layouts.

Phase B (larger): Add a Supabase lakehouse (graph_runs summary + graph_entities + graph_edges) per the canonical-3-table-observability-pattern; ship YAML taxonomies under ~/repos/gbautomation/second-brain/knowledge/taxonomies/; ship a count_by_taxonomy() helper in resources/lib/taxonomy.py that TAC builds + proof-vetting-agents can call to make verifiable countable claims. Add a thin Hermes-side skill at ~/.hermes/skills/devops/graphify-sync/ that points at the gbautomation-repo runtime (option C dual-publish pattern from existing skills like linear-github-automation).

Why now

  1. graphify-sync is broken today. Tonight's log: 5 repos errored, 4 skipped, 0 actually synced (cite: ~/.openclaw/logs/graphify-sync.log 2026-05-18). The SSH layer was a vestige of the multi-host era when graphify ran on a remote Mac Mini from a laptop. Hermes consolidated everything onto the Mac Mini in May 2026; SSH-to-self is now pure overhead.
  2. TAC builds fabricate counts. Pitfall #29 in ~/.hermes/skills/autonomous-ai-agents/tactical-agentic-coder/SKILL.md -- sales decks have invented metrics ("9-day Fisch deployment", "Sylvan daily Co-Pilot since 2026") because there's no programmatic source of truth for "how many builds shipped", "how many entities in this client's graph", "how many decisions tagged X".
  3. The taxonomy stubs are dead weight. ~/repos/gbautomation/second-brain/knowledge/entities/{pipeline-taxonomy,33-project-taxonomy}.md were auto-generated by update-wiki with status: unknown and Role: _TBD_. They've been stubs since 2026-04-29 (verified by frontmatter date) and have never been filled in. Real taxonomies need to be machine-readable (YAML), not markdown stubs.

Success criteria

  1. python3 ~/repos/gbautomation/resources/skills/graphify-sync/scripts/graphify_sync.py --dry-run exits 0 with errors=0 and every configured repo classified as (would-update | skipped | unchanged). No SSH calls in the codebase (grep verification).
  2. After 1 live run on gbautomation + fisch-group: 2 rows in Supabase graph_runs, N rows in graph_entities, M rows in graph_edges (N+M >0).
  3. Five seed taxonomies exist as YAML: entity_types, edge_types, client_tiers, build_statuses, skill_categories. Each has >=5 enumerated values with definitions.
  4. from resources.lib.taxonomy import count_by_taxonomy; count_by_taxonomy("build_statuses", "shipped", window="7d") returns an int >=0 backed by a real Supabase query.
  5. Hermes-side skill pointer at ~/.hermes/skills/devops/graphify-sync/SKILL.md exists and contains a runtime_source: field pointing at the gbautomation-repo path.
  6. Migration of existing per-client graphify-out/ directories into the lakehouse: at least the gbautomation graphify-out/graph.json is loadable + queryable from Supabase after backfill.

Non-goals

  • Make graphify itself faster, prettier, or smarter (we use it as-is).
  • Build a UI for browsing the lake (Supabase + SQL is enough for now).
  • Multi-tenant lake isolation (per-client tagging on rows is sufficient; full RLS deferred).
  • Cross-client entity deduplication (each client's graph stays separate).
  • Real-time push (cron-driven daily/hourly is fine; cron defined in Phase A.5).

Why the two-skill layout (option C)

Same pattern as linear-github-automation and kanban-linear-sync in ~/.hermes/skills/devops/. The gbautomation-repo path is the runtime + tests; the Hermes-skill path is a pointer + quick-start doc that loads when an agent calls skill_view(name='graphify-sync'). Keeps runtime changes versioned in the gbautomation repo (where CI/cron lives) without forcing Hermes to vendor a copy.

Why local subprocess instead of SSH

The existing ssh(host, cmd) function in scripts/graphify_sync.py lines 36-43 routes every find and every graphify invocation through ssh greg@100.88.4.114 'export PATH=...; <cmd>'. The IP 100.88.4.114 is the Mac Mini's Tailscale address. When the script RUNS on the Mac Mini, it's SSHing to itself, which requires a self-SSH key configured plus sshd accepting local connections, neither of which is set up. The local-shell rewrite collapses to:

def shell(cmd, timeout=30, cwd=None):
    return subprocess.run(cmd, shell=True, capture_output=True, text=True,
                          timeout=timeout, cwd=cwd)

Plus Path.expanduser() on the repo path. No SSH key management, no Tailscale latency, no ConnectTimeout=10 budget.

Why YAML taxonomies (not markdown)

Markdown is for humans; agents need a structured contract. YAML schema:

# second-brain/knowledge/taxonomies/build_statuses.yaml
name: build_statuses
description: Lifecycle states for a TAC build (Linear-issue + cron-pipeline view)
values:
  - id: drafted
    label: Drafted
    description: PRD in inbox or under review; no Linear issue yet.
  - id: queued
    label: Queued
    description: Linear issue exists with automation/approved label; picker hasn't grabbed it yet.
  - id: building
    label: Building
    description: Cron picked it up; auto/<slug> branch exists; orchestrator running.
  - id: review
    label: Review
    description: PR opened; awaiting human or LLM review pass.
  - id: shipped
    label: Shipped
    description: PR merged to main and Linear issue moved to Done.
  - id: failed
    label: Failed
    description: Cron picked it up but the build failed; PR not opened OR opened with failing CI.
related_supabase_columns:
  - table: graph_runs
    column: build_status
  - table: linear_issues
    column: state

Each taxonomy lives in its own file. The count_by_taxonomy() helper inspects the YAML to know which Supabase column to query.

Section 8 Data Contracts

Supabase schema (additive, no existing-table mutation)

-- 1. graph_runs (one row per graphify invocation)
CREATE TABLE IF NOT EXISTS public.graph_runs (
  run_id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  repo_id           text NOT NULL,
  started_at        timestamptz NOT NULL DEFAULT now(),
  ended_at          timestamptz,
  status            text NOT NULL CHECK (status IN ('success','failed','partial','skipped')),
  files_added       int NOT NULL DEFAULT 0,
  files_modified    int NOT NULL DEFAULT 0,
  files_deleted     int NOT NULL DEFAULT 0,
  graph_path        text,
  build_status      text,
  raw_report        jsonb,
  error_message     text,
  created_at        timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS graph_runs_repo_started_idx ON public.graph_runs (repo_id, started_at DESC);
CREATE INDEX IF NOT EXISTS graph_runs_status_idx ON public.graph_runs (status);

-- 2. graph_entities (flattened from graph.json per run)
CREATE TABLE IF NOT EXISTS public.graph_entities (
  entity_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id      uuid NOT NULL REFERENCES public.graph_runs(run_id) ON DELETE CASCADE,
  repo_id     text NOT NULL,
  name        text NOT NULL,
  type        text NOT NULL,
  properties  jsonb NOT NULL DEFAULT '{}'::jsonb,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS graph_entities_run_idx ON public.graph_entities (run_id);
CREATE INDEX IF NOT EXISTS graph_entities_repo_type_idx ON public.graph_entities (repo_id, type);

-- 3. graph_edges (flattened from graph.json per run)
CREATE TABLE IF NOT EXISTS public.graph_edges (
  edge_id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id             uuid NOT NULL REFERENCES public.graph_runs(run_id) ON DELETE CASCADE,
  repo_id            text NOT NULL,
  source_entity_id   uuid REFERENCES public.graph_entities(entity_id) ON DELETE SET NULL,
  target_entity_id   uuid REFERENCES public.graph_entities(entity_id) ON DELETE SET NULL,
  type               text NOT NULL,
  properties         jsonb NOT NULL DEFAULT '{}'::jsonb,
  created_at         timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS graph_edges_run_idx ON public.graph_edges (run_id);
CREATE INDEX IF NOT EXISTS graph_edges_repo_type_idx ON public.graph_edges (repo_id, type);

-- RLS: service role only
ALTER TABLE public.graph_runs ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.graph_entities ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.graph_edges ENABLE ROW LEVEL SECURITY;
CREATE POLICY service_role_all_graph_runs ON public.graph_runs FOR ALL TO service_role USING (true);
CREATE POLICY service_role_all_graph_entities ON public.graph_entities FOR ALL TO service_role USING (true);
CREATE POLICY service_role_all_graph_edges ON public.graph_edges FOR ALL TO service_role USING (true);

count_by_taxonomy() contract

def count_by_taxonomy(name: str, value: str,
                      window: str = "all",
                      repo_id: str | None = None) -> int:
    """Return count of rows in the Supabase table backing this taxonomy where
    `column = value`, optionally filtered by repo_id and time window.

    name:   taxonomy name (matches YAML filename without extension)
    value:  one of the YAML's values[].id (validated; raises ValueError on miss)
    window: 'all' | '7d' | '30d' | '90d'
    repo_id: optional filter (only if the target table has a repo_id column)

    Returns int. On Supabase unreachable: reads from
    ~/.hermes/observability-fallback.jsonl and counts matching pending rows
    so the answer is never wrong-by-zero.
    """

Pitfall additions (new, since 2026-05-15 evidence)

Pitfall A: do not call the universal skill-run logger from inside graphify-sync.

The Stop hook in GBA-447 already auto-wraps every skill invocation. If graphify-sync

calls record_skill_run() directly, we get duplicate rows (one from the hook,

one from the explicit call). Solution: the lake-writer-agent only writes

skill_outputs rows (referencing the run_id surfaced by the auto-registration

hook), never skill_runs rows. If parent_run_id is needed for nesting under a

cron tick, derive from environment (HERMES_PARENT_RUN_ID or the auto-hook context).

Pitfall B: graph.json file size can exceed Supabase row limit.

Some graphs (eagle-app, when revived) may produce graph.json >1MB. Supabase rows

cap at ~8MB but pagination should kick in earlier for query performance.

lake-writer-agent paginates entities at 100/row and edges at 200/row. The

graph_entities projection is unaffected (one row per entity).

Pitfall C: backfill should reuse auto_registered=true flag.

GBA-447 introduced this column specifically to mark hook-emitted rows vs manual

inserts. Backfill rows should set auto_registered=true AND invoked_by='backfill:2026-05-18'

so an operator can later distinguish hand-inserted history from real cron history.

What this saves

  • 2 fewer Supabase tables (was 3 new, now 1 new)
  • 1 fewer writer function (skill_runs auto-writes via hook)
  • ~120 lines of redundant migration SQL
  • ~80 lines of redundant Python in graph_lake_writer.py
  • 0 new replay scripts (reuse replay_skill_runs_fallback.py)
  • 0 new launchd plists for replay (reuse com.gbautomation.skill-runs-replay.plist)
  • Free integration with skill_metrics_daily materialized view (p50/p95 latency rollups for graphify-sync visible in Supabase dashboard from day 1)
  • Free integration with the universal Stop hook (graphify-sync gets the same observability layer as the other 337 registered skills)

import json, os, urllib.request, urllib.error, uuid
from pathlib import Path
from datetime import datetime, timezone

FALLBACK = Path.home() / ".hermes/observability-fallback.jsonl"
SUPABASE_URL = os.environ.get("SUPABASE_URL")  # set by cron-runner from AWS SM
SUPABASE_KEY = os.environ.get("SUPABASE_SERVICE_KEY")


def _post(table: str, payload: dict) -> str | None:
    """Returns row id on success, None on failure (with fallback write)."""
    if not (SUPABASE_URL and SUPABASE_KEY):
        return _fallback(table, payload, "no_creds")
    try:
        req = urllib.request.Request(
            f"{SUPABASE_URL}/rest/v1/{table}",
            data=json.dumps(payload).encode(),
            headers={
                "apikey": SUPABASE_KEY,
                "Authorization": f"Bearer {SUPABASE_KEY}",
                "Content-Type": "application/json",
                "Prefer": "return=representation",
            }, method="POST")
        with urllib.request.urlopen(req, timeout=10) as resp:
            row = json.loads(resp.read())
            return row[0].get(f"{table.rstrip('s')}_id") if isinstance(row, list) else None
    except (urllib.error.URLError, urllib.error.HTTPError, json.JSONDecodeError, TimeoutError) as e:
        return _fallback(table, payload, f"exc:{type(e).__name__}")


def _fallback(table: str, payload: dict, reason: str) -> None:
    FALLBACK.parent.mkdir(parents=True, exist_ok=True)
    with FALLBACK.open("a") as f:
        f.write(json.dumps({
            "_table": table, "_replay_needed": True,
            "_uuid": str(uuid.uuid4()), "_reason": reason,
            "_emitted_at": datetime.now(timezone.utc).isoformat(),
            "payload": payload,
        }) + "\n")
    return None


def write_run(repo_id, started_at, ended_at, status, files_added, files_modified,
              files_deleted, graph_path=None, raw_report=None, error_message=None):
    return _post("graph_runs", {
        "repo_id": repo_id, "started_at": started_at, "ended_at": ended_at,
        "status": status, "files_added": files_added,
        "files_modified": files_modified, "files_deleted": files_deleted,
        "graph_path": graph_path, "raw_report": raw_report,
        "error_message": error_message,
    })

Section 13 Risks

Risk 1: Graphify CLI binary not present or version-drift

Likelihood: Medium. Mitigation: scaffold-agent verifies which graphify succeeds AND graphify --version returns parseable output. docs-research-agent pins the version in ai_docs/graphify-reference.md. If absent: graphify-sync logs status=skipped reason=no_graphify_binary and moves on. Pipeline keeps working without it (just no fresh graphs).

Risk 2: Cron permissions can't read all client repo dirs

Likelihood: Low. Mitigation: all client repos live under ~/repos/ owned by greg; cron runs as greg. Test against every configured repo in config-paths-agent.

Risk 3: Supabase service role key expires or rotates

Likelihood: Low (rotates infrequently). Mitigation: graph_lake_writer.py reads from env vars (SUPABASE_URL + SUPABASE_SERVICE_KEY) which the cron-runner pulls from AWS SM at startup (same pattern as outbound_supabase_writer.py). If creds stale, writes hit the JSONL fallback and the existing replay cron retries.

Risk 4: YAML taxonomy file gets edited by a human into invalid YAML

Likelihood: Medium. Mitigation: taxonomy.py _load() raises a clear ValueError on parse failure. taxonomy_validate_drill (weekly cron) catches drift. Pre-commit hook lints YAML files.

Risk 5: count_by_taxonomy() returns 0 because Supabase is empty (no rows yet, not because nothing matches)

Likelihood: HIGH on first run post-merge. Mitigation: backfill-agent runs BEFORE the first cron tick; pre-merge smoke test confirms at least 1 row per backfilled repo. Documented in SKILL.md: "Returns 0 means 0 matching rows, not 'unknown'. Confirm rows exist with gbauto-supabase sql 'SELECT count(*) FROM graph_runs'."

Risk 6: graphify produces a malformed graph.json

Likelihood: Medium (graphify is upstream). Mitigation: parse_graph_output() wraps the JSON load in try/except; on failure logs status=partial and inserts the graph_runs row WITHOUT entities/edges. Operator gets a count of partial runs in the weekly report.

Risk 7: Hermes-skill pointer at ~/.hermes/skills/devops/graphify-sync/ drifts from gbautomation-repo runtime

Likelihood: Medium over time. Mitigation: Pointer SKILL.md has runtime_source: field which gets verified by a weekly cron (graphify_skill_pointer_check). On drift, the SKILL.md gets auto-updated with a stale-pointer warning surfaced in the next skill_view call.

Risk 8: SSH removal misses a callsite, agent ships partially-SSH'd code

Likelihood: Low. Mitigation: tests/test_no_ssh.py greps the entire skill directory for the SSH patterns; commits with any match fail the gate. Belt-and-suspenders: also greps ssh (with trailing space) and the literal Tailscale IP.

Risk 9: Migration script over-inserts on retry (Pitfall #24)

Likelihood: Low. Mitigation: backfill is keyed on (repo_id, started_at) UPSERT semantics. tests/test_backfill_idempotent.py runs twice and asserts row count unchanged.

Risk 10: PR validation passes but the live cron breaks (Pitfall #25 sandbox-test)

Likelihood: Medium. Mitigation: scaffold-agent's scripts/scaffold_check.sh is sandbox-tested with HOME=/tmp/sandbox-graphify </dev/null. Validates no interactive prompts, no implicit mkdir -p failures.

Risk 11: Em-dash creep in YAML/Python docstrings

Likelihood: Low. Mitigation: Pre-commit hook AND grep -c "--" over every modified file before commit.

Risk 12: Subagent "OK file written" trap (Pitfall #27)

Likelihood: Medium. Mitigation: After every phase, orchestrator runs bash ~/.hermes/skills/devops/check-disk-state/scripts/check-disk-state.sh ~/repos/gbautomation <files> and fails the phase if ORIGIN_OK isn't green.
