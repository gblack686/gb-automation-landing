  2. The Langfuse leg is a no-op — open_langfuse_span() builds a dict and hard-codes

    3. posted=False. No trace/observation/generation/score is ever POSTed, so the 1h-smoke acceptance "every tick has a trace" is unsatisfiable. The advanced emitter already exists. (3 agents)

03 Workstream A — Supabase schema completion (P0) 425 words

A1. Author hermes_cron_catalog migration (missing-table, high — 3 agents)

run_managed_cron.py:93,640 upserts CATALOG_TABLE='hermes_cron_catalog' on-conflict name; sync_cron_catalog.py:47,126 and sprint-manager-cron/run.py:490 + artifact-save-cron/run.py:322 also write it. No .sql defines it anywhere — columns live only in the phase4 plan markdown. build_catalog_row (run_managed_cron.py:523-541) sends 13 keys un-projected (no _project guard), so the table must expose all of them.

  • Action (PC): author supabase/migrations/20260617020000_create_hermes_cron_catalog.sql:

    • name text primary key, host, profile, schedule, mode default 'managed', script_or_skill, bucket default 'gap', state default 'active', openclaw_twin, last_green_at timestamptz, manifest_synced_at timestamptz, schema_version int default 1, tenant text not null default 'gbautomation', created_at, updated_at + index (tenant, name) + RLS mirroring host-job-data-output/references/migrations.sql.

  • A1a — last_green_at monotonicity (column-mismatch, med): build_catalog_row:537 sends

    • last_green_at=None on non-ok ticks; a blanket on-conflict SET would clobber the watermark, defeating the docstring's "advance last_green_at iff outcome=ok." Make it monotonic: last_green_at = COALESCE(EXCLUDED.last_green_at, hermes_cron_catalog.last_green_at).

  • A1b — cron_id reconciliation: sync_cron_catalog.py:14-17 lists cron_id as canonical but

    • neither row builder emits it. Decide: add to the migration + both builders, or drop from the doc.

A2. Apply the three Mini-side migrations (unapplied-migration, high)

DDL fails DNS from the PC (SELECT works); apply on the Mac Mini via gbauto-supabase migrate. The supabase_migrations ledger is stale (2 of 31 recorded) — judge applied-state by table/constraint existence, not the ledger. Apply order:

  1. supabase/migrations/20260617000000_create_prompt_profile_applies.sql — unblocks Canopy

    2. ship_prompt_profile_apply.py. (Not on the cron hot path.)

  2. NEW 20260617020000_create_hermes_cron_catalog.sql (A1) — unblocks the catalog leg.
  3. resources/skills/hermes-cron-manager/migrations/20260617010000_cron_run_outputs_managed_status.sql

    4. — only if adopting Strategy B (see A3). Also: this file lives outside supabase/migrations/ so the standard migrate flow won't pick it up — move or document it.

  • Validation: re-run a --inline (live) managed tick; assert write_result.hermes_cron_catalog.ok

    • and write_result.cron_run_outputs.ok are both true; readback via gbauto-supabase --json query (POSIX ~*, never LIKE %).

A3. cron_run_outputs.status — Strategy A vs B (decision)

Live cron_run_outputs_status_check = {pr_opened, pushed_no_pr, noop, failed_silent, error, timeout} (a real CHECK, not free text). Strategy A (default OUTPUT_STATUS_MAP = {ok:noop, partial:failed_silent, fail:error}) passes today, zero DDL. Strategy B (managed_ok/partial/fail) needs migration #3 applied first or every insert violates the CHECK. Recommendation: keep Strategy A unless dashboards must distinguish managed ticks from legacy dispatch outputs. The two constants + the migration must move in lockstep.

A4. Clean legs (no action) (low)

cron_runs, cron_run_outputs, host_job_runs, agent_runs were verified structurally clean — the _project() tuples (CRON_RUNS_DB_COLS/CRON_OUTPUTS_DB_COLS) are the reason they don't silently fail; keep them in lockstep when adding columns. (Note: host_job_runs content is non-conforming — see Workstream C.)

B1. Wire the emitter (high)

In run_managed_cron.py, replace the dead open_langfuse_span() with a call to resources.lib.tracing.emit_eagle_graph_trace(name=f'managed-cron:{name}', harness='hermes', platform='cron', trigger=f'managed_cron:{name}', generation={'model': manager_model, 'output': assessment, 'usage': <token usage>}, chain={'name':'assess','output':metrics}, tags=langfuse_tags, metadata={'session_id': tick_id, 'tenant': tenant, 'environment': host_class}); capture trace_id/trace_url into the receipt + card.

B2. Post the manager verdict as a score (high)

The manager IS an LLM judge. After emitting the trace, post manager_outcome (ok=1/partial=0.5/ fail=0) and cost_usd scores via a reuse of post_langfuse_scores._post_score (factor it into tracing.py as post_score(); add the names to VALID_SCORE_NAMES).

B3. Capture token usage (high)

Extend _coerce_assessment (run_managed_cron.py:363) + assess_hermes/assess_claude_subprocess to return token usage, and populate GENERATION.usageDetails (closes the "token usage populated: 0" gap from 2026-06-10-langfuse-backed-build-report-design.md:66).

B4. Extend the tag schema (med)

required_langfuse_tags() (run_managed_cron.py:577) + LANGFUSE_BASE_TAGS in the validator + the 5 managed.yaml langfuse_tags blocks should add harness:hermes, platform:cron, trigger:managed_cron:<name>, env:<host_class>, model:<manager_model>. Prefer tracing.eagle_trace_tags()/eagle_trace_metadata() so the stack inherits the canonical contract. Decision: enforce as hard gate now, or metadata-only until source emission is proven by the smoke? Recommendation: metadata-only first; gate after B1–B3 land and the smoke shows green read-back.

B5. Trace-verify test (high — also closes the smoke gap)

Add a creds-gated test (skip-when-absent, mirroring tests/test_check_langfuse_logs.py) that runs a live tick and asserts check_langfuse_logs.read_trace_by_id() returns the emitted trace_id with ≥2 observations and non-empty usage. This is what makes the 1h-smoke "every tick has a trace" acceptance satisfiable. Mirror new traces into langfuse_traces via sync_langfuse_traces_to_supabase.py for the dossier join.

05 Workstream C — Receipt-contract conformance + test coverage (P0/P1) 453 words

C1. Conform host-job-run.v1 (column-mismatch, high)

build_host_job_receipt (run_managed_cron.py:491-520) violates host-job-data-output/references/host-job-run.schema.json on 5 fields:

  1. run_id=managed-cron:{name}:{tick} ✗ pattern ^(mm|st|hj)-… → emit hj-<YYYYMMDDTHHMMSSZ>-<slug>.
  2. status=outcome where 'fail' ✗ enum {ok,failed,skipped,blocked,partial} → map fail→failed

    3. (a raw fail already pollutes the canonical table — host_job_runs.status has no CHECK).

  3. execution omits required started_at + duration_seconds (emits elapsed_s/ended_at).
  4. host_class='mac-mini' triggers the conditional requiring pathway/source/request/skill_chain;

    5. pathway='hermes-cron-managed' ✗ enum, source missing system, request+skill_chain absent.

  • Decision: keep host_class='mac-mini' (and add the required shape) vs set 'other' to skip the

    • conditional. Either way the run_id/status/execution fixes are mandatory.

C2. Wire the canonical validator into tests (missing-test, high)

host-job-data-output/tests/test_schema.py jsonschema-validates against the canonical schema; the cron stack never uses it (insert_host_job_run_to_supabase.py:121 checks only schema_version). Add the validator to test_run_managed_cron.py and optionally an envelope-conformance sub-check to hermes-ci-gate so future receipt-builder drift fails the gate.

C3. Live persistence round-trip test (missing-test, high — 2 agents)

The single path that inserts into Supabase (write_receipts, run_managed_cron.py:628) is never run under test — every test passes --stub (offline). Add an env-gated (HCM_LIVE_TEST=1) end-to-end non-stub tick that asserts cron_runs/cron_run_outputs/host_job_runs/agent_runs rows insert + read back (status accepted, agent_summary non-empty, ids match). Also untested: build_card_row + Kanban upsert_row, the Langfuse leg (B5), and the morning-brief digest content/deliver_origin.

C4. Unify (or contract-test) the forked receipt chain (missing-integration, high — DECISION)

Only morning-brief-cron delegates to run_managed_cron.py; git-sync, prd-index, sprint-manager, artifact-save each ship a parallel run.py with divergent receipt schemas (e.g. git-sync writes 7 local JSON files; sprint-manager rows lack tick_id/issue_id). The wrapper docstring claims it's the one true path. Decision required:

  • (a) Unify — make each skill's run.py a thin tool returning a JSON summary; let

    • run_managed_cron.py own all 7 receipt legs (the morning-brief pattern). Deletes the per-skill receipt code. (Recommended — single contract, single test surface.)

  • (b) Keep two-tier — add a contract test per skill asserting its row shapes match the real DB

    • columns. Documents the divergence as intentional.

C5. Surface dead receipt legs (missing-integration, med)

write_receipts swallows leg failures; the tick still returns exit 0 and the digest still says outcome:ok even with the catalog leg failing 100%. Promote leg failures into the managed-run.v1 risk list + the morning-brief digest, and run validate-cron-deploy before declaring crons live.

C6. Gate the per-skill descriptors (missing-integration, med)

hermes-ci-gate's managed_manifest check only validates the central crons.manifest.yaml (which rc2-skips by design), so the gate never validates the 5 per-skill managed.yaml. The test_managed_yaml_descriptors.py guard runs only in pr-validate.yml. Add a 6th gate sub-check (or point HERMES_CI_GATE_MANIFEST_FILE per-descriptor) so the merge-gating gate covers them too.
