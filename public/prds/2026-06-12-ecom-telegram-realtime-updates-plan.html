01 Overview 212 words

Design principle: start (members get exactly one notification); every ~75s a sidecar reads progress_heartbeat.json and calls editMessageText on the same message_id; the final edit carries the verdict. No scroll spam, fully realtime, and Telegram doesn't re-notify on edits. Separate one-shot lines only for block escalations and production-gate transitions.

Message contract (3 lines max, dense): 🕷 vans-com #0035 ⏳14m 🔁1/2 🛍 312/2000 · 💰 287 · 📄 3/42 · 🧭 scrolling ⏰ cap 45m · hb 01:52:14

Implementation (3 small pieces): 1. ecom_runtime/notify.py: add edit_message(token, chat_id, message_id, html) (editMessageText, swallow "message is not modified" errors) + build_live_status_html(heartbeat, checkpoint, target) for the 3-line format. 2. ecom_runtime/cli.py live-status subcommand: loop — read progress_heartbeat.json + scrape_checkpoint.json every --interval 75; first tick sendMessage (store {message_id, chat_id} in <run-dir>/telegram_live_message.json — survives runner attempts since the run dir is shared); subsequent ticks edit; exit + final edit when the runner pid dies and summary.json/runs.jsonl verdict lands. --dry-run prints instead of sending. 3. vans.sh: launch the sidecar alongside the runner (python3 -m ecom_runtime.cli live-status --run-dir outputs/crawl/vans-com --interval 75 &), reusing the existing lock lifecycle. Gate transitions: a tiny gate_notify step appended to the runner epilogue compares ecom_website_production_status against a state file (same edge-trigger pattern as scripts/kanban_crash_storm_alert.py) and posts 🏁 lines on change.

02 Design principle 92 words

One message per run, edited in place. sendMessage fires once at run start (members get exactly one notification); every ~75s a sidecar reads progress_heartbeat.json and calls editMessageText on the same message_id; the final edit carries the verdict. No scroll spam, fully realtime, and Telegram doesn't re-notify on edits. Separate one-shot lines only for block escalations and production-gate transitions.

Channel: the existing ecom log channel — ecom_runtime/notify.py:resolve_telegram_config(channel="log") (ECOM_TELEGRAM_LOG_CHAT_ID / AWS log_chat_id) already resolves it, and _post_telegram already returns message_id (notify.py:229). The missing primitive is one function: edit_message().
