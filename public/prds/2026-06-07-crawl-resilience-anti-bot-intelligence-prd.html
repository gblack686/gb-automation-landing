02 Overview 133 words

The mall-scanner pipeline goes silent or fails when a target site (Instagram first, protected apparel sites next) returns a bot wall, a rate-limit, or an empty JSON payload — and today it has no way to tell those apart, no way to escalate past them, and no way to retry intelligently. This PRD specifies a shared crawl-resilience layer: a block classifier, a tiered escalation ladder, type-aware retry handlers, and a fixture test harness — usable by both the mall-scanner (mall_) and shop-intelligence (ecom_) runtimes.

The goal is not a magic "bypass everything" engine. It is to make the scraper honest about why it failed and correct about what to try next, so a run ends in a true ok | empty | blocked_bot_wall | rate_limited | login_required verdict with evidence — and reaches the data when a legitimate path exists.

03 Problem 212 words

Three concrete failures, observed and root-caused 2026-06-07:

  1. Instagram path is brittle and terminal. The scraper hits IG's

    2. web_profile_info JSON endpoint first (this is what produced the 2026-05-18 baseline of 12 posts). IG has since clamped that endpoint for unauthenticated / datacenter callers (401/429). Because IG is classified as "has a JSON path," the router treats the failure as terminal and never escalates to the browser harness fallback. Result: empty or failed, no retry, no signal.

  1. No block intelligence. Failures surface as a bare stderr tail written

    2. to scrape_runs.failure_reason (scripts/mall_scanner_poller.py:157-170). There is no taxonomy distinguishing "rate-limited, back off and retry" from "login required, stop" from "real bot wall." The poller does zero retries and re-queueing is manual.

  1. The "it just works" expectation is mis-set. browser-use/browser-harness

    2. has no local stealth engine — the word "stealth" appears once in the repo (README.md:43) describing a Browser Use Cloud tier, not a local flag. The harness gets through DataDome/Cloudflare/PerimeterX only by presenting a real Chrome's genuine TLS/JA3 fingerprint via CDP (documented per-site in agent-workspace/domain-skills/*/scraping.md, gated behind BH_DOMAIN_SKILLS=1). Run headless on the Mini with no logged-in session and no residential egress, that thesis breaks — which is the configuration we are (probably) in.

04 Goals 115 words
  • Classify every scrape outcome into a structured verdict with evidence, not a

    • raw stderr tail.

  • Replace terminal single-attempt behavior with a **type-aware escalation

    • ladder** (cheap → expensive) that stops on verdicts that retry can't fix.

  • Make Instagram escalate to a real authenticated browser session when the JSON

    • endpoint is blocked, instead of dead-ending.

  • Stand up a Crawl4AI probe path (stealth mode → undetected adapter →

    • proxy/fallback) as the programmatic tier alongside browser-harness's real-Chrome tier.

  • Turn on and extend browser-harness domain-skill intelligence

    • (BH_DOMAIN_SKILLS=1; add an instagram/ skill).

  • Ship a fixture-based test harness so block detection is validated against

    • saved challenge pages, not debugged live against a moving target.

  • Emit the verdict + tier-resolved-by into existing telemetry

    • (scrape_runs / ecom_runs).

05 Non-goals 132 words
  • Not solving CAPTCHA-farm-grade or behavioral-biometric walls. Where a

    • legitimate authenticated/residential path doesn't exist, the correct output is still blocked_bot_wall with evidence — we stop, we don't brute-force.

  • Not scraping anything outside the client's legitimate interest (The Mall App's

    • own IG, its featured/partner brands, public apparel catalogs). No credential stuffing, no auth bypass, no ToS-violating volume.

  • No secrets in reports, fixtures, or frontend code.
  • Not rewriting the mall-scanner data plane — this layer plugs into it.

Stance change (explicit): the 2026-06-07 mall-scanner PRD listed "No anti-bot bypass" as a non-goal and said to "stop cleanly on anti-bot walls." This PRD narrows that: we now do build resilience and legitimate escalation (authenticated sessions, residential egress, real-browser fingerprint, stealth-mode crawling), while keeping the hard line at CAPTCHA-farming and ToS-violating bypass. Approve this reversal before build.

10 Acceptance Criteria 97 words
  • Given the saved fixture set, classify_block() tags vendor + verdict

    • correctly for ≥1 each of Cloudflare, DataDome, PerimeterX, and IG-429.

  • A blocked IG web_profile_info run escalates to the real-browser tier

    • instead of returning terminal empty.

  • One previously-failing target either (a) resolves via a higher tier and

    • records tier_resolved_by, or (b) returns blocked_bot_wall/login_required with a captured signal — never a bare stderr tail.

  • rate_limited/transient_error get exponential-backoff retries; captcha/

    • login_required stop immediately (verified in a retry-policy unit test).

  • Telemetry rows carry verdict, vendor, tier_resolved_by, attempts.
  • BH_DOMAIN_SKILLS=1 is set in the mall-scraper invocation and an

    • instagram/ domain skill exists.

11 Risks 148 words
  • RISK: anti-bot is probabilistic and adaptive — a tier that works today may

    • fail tomorrow. Mitigation: classifier + telemetry make regressions visible; we don't promise 100%.

  • RISK: residential proxy / Browser Use Cloud spend. Mitigation: order tiers

    • cheap→expensive; gate Tier 2/3 behind operator-approved budget.

  • RISK: Instagram authed-session scraping carries account/ToS exposure.

    • Mitigation: use a dedicated non-primary IG session, conservative volume, client-relevant handles only; stop at login_required.

  • RISK: stance reversal needs operator sign-off before any bypass code lands.

    • Mitigation: this PRD blocks on the explicit approval above.

  • OPEN: confirm the live failure mode — pull the last N scrape_runs.failure_reason

    • rows via gbauto-supabase before building, so the classifier is seeded from real signals, not inferred ones.

  • OPEN: adopt Crawl4AI as a vendored dependency vs. copy only its classifier

    • taxonomy? (Recommend: start with the taxonomy + a thin Crawl4AI probe script, vendor fully only if Tier 1 proves it earns its place.)
